### What is the `ramping-vus` executor?

The **`ramping-vus`** executor in **k6** is used when you want the number of **Virtual Users (VUs)** to **increase or decrease over time** instead of staying constant throughout the test.

This makes it very useful for simulating **real-world traffic patterns**, because in real systems, traffic usually does not stay flat:

- users gradually arrive
- load builds up
- traffic reaches a peak
- then it drops again

So instead of saying:

> “Run 10 users for 30 seconds”

you can say:

> “Start from 0 users, ramp up to 10 users in 20 seconds, then ramp down back to 0 in 10 seconds.”

That is exactly what `ramping-vus` is designed for.

---

# Why use `ramping-vus`?

This executor is useful when you want to test how your application behaves under **changing load**.

## Common use cases

- **Load testing with realistic traffic growth**    
- **Stress testing** to find how the system behaves as load increases
- **Scalability testing** to see how performance changes as more users are added
- **Capacity planning** to estimate how much load the system can handle
- **Benchmarking** under low, medium, and peak traffic levels in a single test

---

# Example Script

```javascript
import http from "k6/http";
import { sleep } from "k6";

export let options = {
	discardResponseBodies: true,
	scenarios: {
		contacts: {
			executor: "ramping-vus",
			startVUs: 0,
			stages: [
				{ duration: "20s", target: 10 },
				{ duration: "10s", target: 0 }
			],
			gracefulRampDown: "0s"
		}
	}
};

export default function() {
	http.get("https://test.k6.io/contacts.php");
	
	sleep(1);
}
```

# Understanding the executor settings

## `executor: "ramping-vus"`

```javascript
executor: "ramping-vus"
```

This tells k6 to use the **ramping virtual users executor**.

Instead of keeping the number of users fixed, k6 changes the number of active VUs **based on the stages you define**.

---

## `startVUs: 0`

```javascript
startVUs: 0
```

This is the **initial number of VUs** when the test starts.

So here:

- the test begins with **0 virtual users**
- then k6 follows the stages to increase or decrease the VU count

You could also start with a non-zero value, for example:

```javascript
startVUs: 5
```

which would begin the test with 5 users already active.

---

# The `stages` array

```javascript
stages: [
	{ duration: "20s", target: 10 },
	{ duration: "10s", target: 0 }
]
```

This is the most important part of the `ramping-vus` executor.

Each stage defines:

- **how long** that stage lasts → `duration`    
- **how many VUs** k6 should reach by the end of that stage → `target`

---

# Stage 1

```javascript
{ duration: "20s", target: 10 }
```

### Meaning:

- Start from the current VU count (**0**, because `startVUs: 0`)    
- Over **20 seconds**, gradually increase the VUs until they reach **10**

This is a **ramp-up** stage.

So the VU count changes roughly like this over time:

- 0 users
- 1 user
- 2 users
- 3 users
- ...
- 10 users by the end of 20 seconds

The increase is gradual, not instant.

---

# Stage 2

```javascript
{ duration: "10s", target: 0 }
```

### Meaning:

- Start from the current VU count (**10** at the end of Stage 1)    
- Over **10 seconds**, gradually reduce the VUs until they reach **0**

This is a **ramp-down** stage.

So the VU count gradually decreases:

- 10 users
- 9 users
- 8 users
- ...
- 0 users by the end of 10 seconds

---

# Total test duration

The total duration of the scenario is the sum of all stage durations:

- Stage 1 = **20s**    
- Stage 2 = **10s**

## Total = **30 seconds**

---

# `gracefulRampDown: "0s"`

```javascript
gracefulRampDown: "0s"
```

This controls what happens to **currently running iterations** when k6 needs to reduce the number of VUs during a ramp-down stage.

---

# What is graceful ramp-down?

Suppose k6 wants to reduce the number of VUs from 10 to 8.

Some of those VUs may currently be in the middle of an iteration:

- maybe they already sent an HTTP request    
- maybe they are sleeping
- maybe they are still processing logic

k6 then has two choices:

1. **Wait for the iteration to finish**
2. **Stop the VU immediately**

`gracefulRampDown` controls how long k6 should wait before forcefully stopping those VUs.

---

## In this script:

```javascript
gracefulRampDown: "0s"
```

means:

- do **not wait at all**    
- if a VU needs to be removed during ramp-down, k6 can stop it immediately
- any in-progress iteration may be interrupted

This can lead to **dropped / interrupted iterations**.

---

# Important note about `gracefulRampDown`

If you set:

```javascript
gracefulRampDown: "5s"
```

then during ramp-down, k6 would wait up to **5 seconds** for a running iteration to finish before terminating the VU.

So:

- `"0s"` = aggressive ramp-down, no waiting    
- `"5s"` = smoother ramp-down, allows iterations to complete

---

# Default function

```javascript
export default function() {
	http.get("https://test.k6.io/contacts.php");
	
	sleep(1);
}
```

This is the code every VU executes in each iteration.

### In each iteration, a VU:

1. sends a GET request to:

```javascript
https://test.k6.io/contacts.php
```

2. sleeps for 1 second    
3. starts the next iteration if it is still active

---

# Step-by-step execution flow

# Test starts

Because:

```javascript
startVUs: 0
```

the test starts with **0 VUs**.

---

# First 20 seconds → Ramp up

During:

```javascript
{ duration: "20s", target: 10 }
```

k6 gradually increases the number of active users from **0 to 10**.

So over time, more and more VUs begin executing the `default` function.

This simulates traffic gradually building up.

---

# Next 10 seconds → Ramp down

During:

```javascript
{ duration: "10s", target: 0 }
```

k6 gradually reduces the number of users from **10 back to 0**.

This simulates traffic decreasing.

---

# End of test

Once the second stage completes, the scenario ends.

## Ramp-down phase

- starts at 10

# Important behavior of `ramping-vus`

Unlike `constant-vus`, the number of VUs is **not fixed**.

Instead, it changes according to the stages.

So in this script:

- VUs are **dynamic**    
- duration is **defined by stage durations**
- iterations are **not fixed**
- load pattern changes over time

---

# Metrics to focus on in the output

## 1) `vus`

Shows the number of active virtual users over time.

For this script, it should:

- begin at **0**    
- rise gradually to **10**
- then fall back to **0**

---

## 2) `iterations`

Shows how many iterations completed in total.

This depends on:

- number of active VUs at a given time    
- request speed
- sleep time
- stage duration

Since the VU count changes, the iteration rate also changes.

---

## 3) `http_reqs`

Total number of HTTP requests made.

Since each iteration sends one GET request, this roughly tracks the number of completed iterations.

---

## 4) `http_req_duration`

Time taken by the HTTP request itself.

Useful for seeing whether performance gets worse as load increases.

---

## 5) `iteration_duration`

Time taken for the whole iteration, including:

- HTTP request    
- `sleep(1)`

---

## 6) `dropped_iterations` / interrupted iterations

If `gracefulRampDown` is too small (like `0s`) and k6 removes VUs while they are in the middle of work, some iterations may be interrupted.

That is why ramp-down settings matter.

---

# What happens because `gracefulRampDown` is `0s`?

During the second stage, k6 reduces VUs from 10 to 0.

If a VU is in the middle of:

- an HTTP request    
- a sleep
- some business logic

k6 may terminate it immediately because it does not wait.

So this setting is faster, but less gentle.

---

# When would you use `gracefulRampDown: "0s"`?

Usually when:

- you want a strict ramp-down    
- you do not care if some in-progress iterations are interrupted
- you want to simulate sudden traffic reduction
- you want faster test completion

---

# When would you use a non-zero graceful ramp-down?

For example:

```javascript
gracefulRampDown: "5s"
```

Use this when:

- you want cleaner results    
- you want in-progress transactions to finish
- you want to avoid dropped iterations
- you are testing workflows that should not be abruptly cut off

# Difference from `constant-vus`

## `constant-vus`

- keeps VUs fixed
- good for steady load

Example:

```javascript
vus: 10
duration: "30s"
```

This means:

- 10 users throughout the whole 30 seconds

---

## `ramping-vus`

- changes VUs over time
- good for realistic load growth and reduction

Example:

```javascript
startVUs: 0,
stages: [
  { duration: "20s", target: 10 },
  { duration: "10s", target: 0 }
]
```

This means:

- ramp from 0 → 10
- then ramp from 10 → 0

---

# Difference from iteration-based executors

## `shared-iterations`

- fixed total iterations shared by all VUs

## `per-vu-iterations`

- fixed iterations per VU

## `constant-vus`

- fixed VUs for a fixed duration

## `ramping-vus`

- variable VUs over time based on stages

---

# Quick comparison table

| Executor            | Main control                    | Best for                            |
| ------------------- | ------------------------------- | ----------------------------------- |
| `shared-iterations` | Fixed total iterations          | Complete a fixed amount of work     |
| `per-vu-iterations` | Fixed iterations per VU         | Equal work per user                 |
| `constant-vus`      | Fixed VUs for a duration        | Steady load                         |
| `ramping-vus`       | VUs increase/decrease over time | Realistic load growth and ramp-down |

## In this script:

- test starts with **0 VUs**
- ramps up to **10 VUs in 20 seconds**
- ramps down to **0 VUs in 10 seconds**

# Final summary

The **`ramping-vus`** executor is one of the most important executors in k6 because it helps simulate **realistic traffic patterns** instead of applying a flat load.

In this example:

- the load starts from **zero**
- gradually increases to **10 concurrent users**
- then gradually decreases back to **zero**
- each active user repeatedly performs the same workflow
- the test is useful for studying:
    - scalability
    - performance under changing traffic
    - behavior during ramp-up and ramp-down

So the main purpose of `ramping-vus` is to answer questions like:

- **How does my application behave as more users gradually arrive?**
- **At what point does response time begin to degrade?**
- **Does the application recover properly when load drops?**
- **Can the system handle changing traffic smoothly?**
