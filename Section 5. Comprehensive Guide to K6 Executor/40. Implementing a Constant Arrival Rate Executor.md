## Introduction

The **`constant-arrival-rate` executor** in K6 is used to generate a **steady and predictable number of iterations over time**, regardless of how long individual iterations take.

Unlike VU-based executors such as `constant-vus` or `ramping-vus`, this executor focuses on **how many iterations should start per time unit** rather than how many users are active at a given time.

This makes it especially useful when you want to simulate a **fixed request rate**, such as:

- **30 requests per second**
- **100 transactions per minute**
- **a steady API traffic pattern over time**

K6 will automatically allocate and use as many VUs as needed (up to the configured limit) to maintain the configured arrival rate.

---

## Why use `constant-arrival-rate`?

This executor is useful when you want to test your application under a **controlled throughput/load pattern** instead of a fixed number of users.

### Typical use cases

- **Load testing** with a constant request rate    
- **Performance benchmarking** under stable traffic
- **Capacity planning** to see how much steady traffic the system can handle
- **Stability testing** under predictable continuous load
- **API testing** where the target is requests/sec rather than user count

---

## How `constant-arrival-rate` works

With this executor, you define:

- **`rate`** → how many iterations should start in each time unit    
- **`timeUnit`** → the interval over which the rate is applied
- **`duration`** → how long the scenario should run
- **`preAllocatedVUs`** → number of VUs created before the test starts
- optionally **`maxVUs`** → upper cap on how many VUs K6 can create if more are needed

K6 then tries to maintain the configured arrival rate by dynamically assigning iterations to available VUs. If existing VUs are not enough to keep up, K6 can allocate more VUs (up to `maxVUs`, if defined).

---

# Code Example

```javascript
import http from "k6/http";
import { sleep } from "k6";

export let options = {
	discardResponseBodies: true,
	scenarios: {
		contacts: {
			executor: "constant-arrival-rate", // maintain a constant iteration arrival rate
			duration: "30s", // total duration of the scenario
			rate: 30, // start 30 iterations per timeUnit
			timeUnit: "1s", // rate is applied every 1 second
			preAllocatedVUs: 50, // VUs created before the test starts
			maxVUs: 100 // optional upper limit if more VUs are needed
		}
	}
};

export default function() {
	http.get("https://test.k6.io/contacts.php");
	sleep(1);
}
```

```javascript

	contacts: {
		executor: "constant-arrival-rate",
```

This creates a scenario named **`contacts`** using the **`constant-arrival-rate`** executor.

The goal is to maintain a **fixed number of iterations per unit time**, not a fixed number of VUs.

---

## 4) Duration of the test

```javascript
duration: "30s",
```

The scenario will run for **30 seconds**.

This means K6 will keep trying to maintain the configured arrival rate for the full 30-second period.

---

## 5) Rate of iterations

```javascript
rate: 30,
timeUnit: "1s",
```

This means:

- Start **30 iterations**    
- every **1 second**

So the target throughput is:

- **30 iterations per second**

If the test runs for 30 seconds, K6 will try to execute approximately:

- **30 × 30 = 900 iterations**

provided the system and the load generator can keep up.

---

## 6) Pre-allocated VUs

```javascript
preAllocatedVUs: 50,
```

K6 creates **50 VUs in advance** before the scenario starts.

### Why is this useful?

It ensures that enough VUs are already available to sustain the desired arrival rate without delay.

If iterations take time (for example, because of network latency, server delay, or `sleep()`), K6 may need multiple VUs active simultaneously to keep starting 30 new iterations every second.

---

## 7) Maximum VUs

```javascript
maxVUs: 100
```

This is optional, but highly useful.

If the pre-allocated VUs are not enough to sustain the configured rate, K6 can create more VUs up to **100**.

### Example

If each iteration takes around **2 seconds**, then one VU cannot start a new iteration every second continuously. K6 may need to use more VUs in parallel to maintain **30 iterations/second**.

---

## 8) Default function

```javascript
export default function() {
	http.get("https://test.k6.io/contacts.php");
	sleep(1);
}
```

Each iteration performs:

1. an HTTP GET request to the endpoint    
2. a 1-second sleep

This simulates a more realistic user interaction instead of sending requests back-to-back with no delay.

# Key Point: Arrival Rate vs VUs

This is the most important concept to understand.

## In `constant-vus`

You say:

> “Keep **10 users active** for 30 seconds.”

K6 keeps the same number of VUs active, and the number of iterations depends on how fast those VUs can execute the script.

---

## In `constant-arrival-rate`

You say:

> “Start **30 iterations every second** for 30 seconds.”

Now the **iteration rate is fixed**, and K6 adjusts the VUs as needed to try to maintain that rate.

So:

- **`constant-vus`** controls **concurrency**    
- **`constant-arrival-rate`** controls **throughput / request rate**

This means:

That’s why `preAllocatedVUs` and `maxVUs` matter.

# When to Use `constant-arrival-rate`

Use this executor when your test objective is based on **request rate / throughput** rather than user count.

## Good examples

- “Send **100 requests per second** to this API.”    
- “Simulate **50 checkout attempts per second**.”
- “Maintain **steady traffic** for 10 minutes.”
- “Benchmark the system under a predictable transaction rate.”

---

# When Not to Use It

Avoid this executor if your goal is specifically to simulate **a fixed number of concurrent users**.

For example, if you want:

- 20 users browsing the site at the same time    
- 100 logged-in users interacting continuously

then **`constant-vus`** or **`ramping-vus`** is usually more appropriate.

The **`constant-arrival-rate` executor** is used when you want to maintain a **fixed number of iterations per unit time**.

- The test runs for **30 seconds**    
- K6 tries to start **30 iterations per second**
- **50 VUs** are pre-allocated

## Main takeaway
