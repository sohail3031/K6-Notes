## Introduction

The **`ramping-arrival-rate` executor** in K6 is used to simulate a load pattern where the **iteration arrival rate gradually increases, decreases, or stays constant across different stages**.

Unlike **VU-based executors** such as `constant-vus` and `ramping-vus`, this executor focuses on **how many iterations should start per unit time**, not on maintaining a fixed number of users.

It is useful when you want to model **real-world traffic patterns** such as:

- traffic gradually increasing during peak hours
- a flash sale where request rate ramps up quickly
- load stabilizing for some time and then dropping
- testing how the system behaves as throughput changes over time

---

# Why use `ramping-arrival-rate`?

This executor is useful when your goal is to control **throughput over time** rather than just the number of concurrent users.

## Typical use cases

- **Load testing** with gradually increasing request rates    
- **Stress testing** to identify breaking points under rising traffic
- **Scalability testing** to see how the application handles growth in demand
- **Performance benchmarking** at different throughput levels
- **Simulating real-world traffic** that rises, plateaus, and falls

---

# How `ramping-arrival-rate` works

With this executor, you define:

- **`startRate`** → the initial number of iterations to start per `timeUnit`    
- **`timeUnit`** → the interval over which the rate is measured
- **`preAllocatedVUs`** → number of VUs created before the test starts
- **`stages`** → how the arrival rate should change over time
- optionally **`maxVUs`** → maximum number of VUs K6 can allocate if more are needed

K6 will then try to maintain the configured iteration rate for each stage by dynamically assigning work to available VUs.

---

# Important Concept: Arrival Rate vs VUs

The **driving factor** in `ramping-arrival-rate` is **iterations per time unit**, not the number of users.

That means:

- you define **how many iterations should start**    
- K6 automatically decides **how many VUs are needed** to achieve that rate

So if iterations take longer, K6 may need to use more VUs.

---

# Corrected Code Example

```javascript
import http from "k6/http";
import { sleep } from "k6";

export let options = {
	scenarios: {
		contacts: {
			executor: "ramping-arrival-rate", // ramp the iteration arrival rate up and down
			startRate: 0, // initial arrival rate at the beginning
			timeUnit: "1s", // rates/targets are measured per second
			preAllocatedVUs: 20, // VUs created before the test starts
			maxVUs: 100, // optional upper cap if more VUs are needed
			stages: [
				{ duration: "20s", target: 10 }, // ramp up to 10 iterations/sec
				{ duration: "20s", target: 20 }, // ramp up to 20 iterations/sec
				{ duration: "20s", target: 20 }, // stay at 20 iterations/sec
				{ duration: "20s", target: 5 }   // ramp down to 5 iterations/sec
			]
		}
	}
};

export default function() {
	http.get("https://test.k6.io/contacts.php");
	sleep(1);
}
```

	{ duration: "20s", target: 300 },

This is **valid syntax**, but the explanation in the lecture was misleading.

## What it actually means

With:

```javascript
timeUnit: "20s"
startRate: 300
```

you are saying:

- start **300 iterations every 20 seconds**    

That is **not** “300 iterations per second”.

### Equivalent per-second rate

- **300 iterations / 20 seconds = 15 iterations per second**
- **600 iterations / 20 seconds = 30 iterations per second**
- **60 iterations / 20 seconds = 3 iterations per second**

So the original explanation saying “300 iterations in 20s” is only partially helpful. The more accurate interpretation is:

- target **300 per 20 seconds**
- then **600 per 20 seconds**
- then stay at **600 per 20 seconds**
- then ramp down to **60 per 20 seconds**

To make the note easier to understand, I rewrote the example using:

```javascript
timeUnit: "1s"
```

because it makes the arrival rate much more intuitive.

# Explanation of the Script

## 1) Importing modules

```javascript
import http from "k6/http";
import { sleep } from "k6";
```

- **`http`** → used to send HTTP requests    
- **`sleep()`** → pauses execution to simulate user think time

---

## 2) Defining the scenario

```javascript
scenarios: {
	contacts: {
		executor: "ramping-arrival-rate",
```

This creates a scenario named **`contacts`** using the **`ramping-arrival-rate`** executor.

The purpose is to **change the request/iteration rate over time**.

---

## 3) `startRate`

```javascript
startRate: 0,
```

This is the **initial arrival rate** at the beginning of the test.

Here it means:

- start from **0 iterations per second**    
- then ramp up according to the defined stages

If you set `startRate: 10` and `timeUnit: "1s"`, the test would begin at **10 iterations per second**.

---

## 4) `timeUnit`

```javascript
timeUnit: "1s",
```

This defines the unit of time used for the arrival rate.

So when a stage says:

```javascript
target: 20
```

it means:

- **20 iterations per second**    

If `timeUnit` were `"1m"`, then `target: 20` would mean:

- **20 iterations per minute**

---

## 5) `preAllocatedVUs`

```javascript
preAllocatedVUs: 20,
```

This tells K6 to create **20 VUs before the test begins**.

These VUs are used to start handling iterations immediately without delay.

This improves test stability and reduces startup overhead.

---

## 6) `maxVUs`

```javascript
maxVUs: 100,
```

This sets an upper limit on how many VUs K6 can allocate if the existing VUs are not enough to sustain the target arrival rate.

### Why this matters

If each iteration takes a long time because of:

- network latency    
- slow server response
- `sleep()`
- complex user flows

then K6 may need more VUs to keep starting new iterations at the required rate.

---

## 7) `stages`

```javascript
stages: [
	{ duration: "20s", target: 10 },
	{ duration: "20s", target: 20 },
	{ duration: "20s", target: 20 },
	{ duration: "20s", target: 5 }
]
```

This defines how the arrival rate changes over time.

---

# Stage-by-Stage Breakdown

## Stage 1

```javascript
{ duration: "20s", target: 10 }
```

For the first **20 seconds**, K6 gradually ramps the arrival rate from the current rate (`startRate = 0`) to **10 iterations per second**.

So during this period:

- traffic increases gradually    
- K6 keeps adjusting VUs as needed

---

## Stage 2

```javascript
{ duration: "20s", target: 20 }
```

For the next **20 seconds**, K6 ramps the arrival rate from **10 iterations/sec** to **20 iterations/sec**.

This simulates increasing traffic.

---

## Stage 3

```javascript
{ duration: "20s", target: 20 }
```

For the next **20 seconds**, K6 keeps the rate at **20 iterations/sec**.

This creates a **steady plateau phase** where the system is tested under sustained traffic.

---

## Stage 4

```javascript
{ duration: "20s", target: 5 }
```

For the final **20 seconds**, K6 gradually reduces the arrival rate from **20 iterations/sec** down to **5 iterations/sec**.

This simulates traffic cooling down after a peak period.

---

# Total Test Duration

The total duration is the sum of all stage durations:

- 20s + 20s + 20s + 20s = **80 seconds**    

So this scenario runs for **80 seconds** in total.

---

# Default Function

```javascript
export default function() {
	http.get("https://test.k6.io/contacts.php");
	sleep(1);
}
```

Each iteration does two things:

1. Sends an HTTP GET request    
2. Sleeps for 1 second

This makes the script behave more like a real user instead of immediately sending requests back-to-back.

# Visualizing the Load Pattern

If we think about the arrival rate graph, it would look like this:

## Phase 1: Ramp-up

- starts at 0 iterations/sec    
- gradually rises to 10 iterations/sec

## Phase 2: More ramp-up

- rises from 10 to 20 iterations/sec

## Phase 3: Plateau

## Phase 4: Ramp-down

- drops from 20 to 5 iterations/sec

So the shape is:

**increase → increase → hold steady → decrease**

# Difference Between `constant-arrival-rate` and `ramping-arrival-rate`

## `constant-arrival-rate`

Use this when you want a **fixed iteration rate** for the whole test.

### Example

- 30 iterations/sec for 30 seconds

The rate stays the same throughout the test.

---

## `ramping-arrival-rate`

Use this when you want the **iteration rate to change over time**.

### Example

- ramp from 10 to 20 iterations/sec
- hold at 20
- drop to 5

This is better for simulating realistic traffic growth and decline.

---

# Difference Between `ramping-arrival-rate` and `ramping-vus`

## `ramping-vus`

You control:

- the **number of VUs**

K6 changes the number of users, and the actual iteration rate depends on how fast those VUs execute the script.

---

## `ramping-arrival-rate`

You control:

- the **number of iterations per time unit**

K6 changes the number of VUs as needed to maintain that iteration rate.

So:

- **`ramping-vus`** → user/concurrency-driven
- **`ramping-arrival-rate`** → throughput/request-rate-driven

---

# When to Use `ramping-arrival-rate`

Use this executor when you want to simulate **changing throughput over time**.

## Good examples

- traffic rising during business hours    
- flash-sale traffic ramping up rapidly
- API request rate increasing as more users join
- testing system stability at multiple throughput levels
- gradually increasing load to identify scaling problems

---

# Practical Example

Suppose you want to simulate this pattern:

- first 2 minutes: traffic gradually increases    
- next 5 minutes: traffic stays high
- last 2 minutes: traffic gradually decreases

This is a great use case for **`ramping-arrival-rate`** because the load is naturally expressed as **requests/iterations over time**, not as a fixed number of users.

---

# Important Notes

## 1) Arrival rate is not the same as completed iterations

K6 tries to **start** the configured number of iterations per time unit.

If the system is slow or the test is under-provisioned, K6 may not always achieve the exact target rate.

---

## 2) More VUs may be needed than expected

If each iteration takes longer because of:

- server latency    
- API delays
- `sleep()`
- browser-like workflows

then K6 may need to allocate more VUs to sustain the target arrival rate.

---

## 3) `preAllocatedVUs` should be chosen carefully

Too few pre-allocated VUs may cause the test to struggle at the beginning because K6 needs to allocate additional VUs during execution.

---

## 4) `timeUnit` changes the meaning of `target`

Always read `target` together with `timeUnit`.

### Example

If:

```javascript
timeUnit: "1s"
target: 50
```

that means:

- **50 iterations per second**    

But if:

```javascript
timeUnit: "1m"
target: 50
```

that means:

- **50 iterations per minute**

---

# Summary

The **`ramping-arrival-rate` executor** is used when you want to simulate a load pattern where the **iteration rate changes over time**.

## In this example:

- the arrival rate starts at **0**
- ramps up to **10 iterations/sec**
- then ramps up to **20 iterations/sec**
- stays at **20 iterations/sec**
- then ramps down to **5 iterations/sec**

K6 automatically adjusts the number of VUs needed to try to maintain these rates.

## Main takeaway

Use **`ramping-arrival-rate`** when your test is about **changing throughput over time**, such as ramping up traffic, sustaining peak traffic, and then reducing traffic gradually.
