In this lecture, we will go through a more comprehensive K6 script that demonstrates **multiple Virtual User configuration options**.

The goal of this example is to understand how different VU-related options work together and, more importantly, which options **cannot** be used together in the same script.

---

# Objective of This Example

This example introduces the following K6 options:

- `vus`
- `duration`
- `stages`
- `iterations`
- `vusMax`
- `startVUs`

We will first look at a script that combines many of these options, and then understand **why some combinations are invalid**.

---

# Initial Script with Multiple VU Options

```javascript
import http from "k6/http";
import { check, sleep } from "k6";

export const options = {
  vus: 10,               // number of virtual users
  duration: "1m",        // fixed duration for the script
  stages: [
    { duration: "30s", target: 10 }, // ramp up to 10 VUs in 30s
    { duration: "30s", target: 20 }, // ramp up from 10 to 20 VUs in 30s
    { duration: "1m", target: 20 },  // stay at 20 VUs for 1 minute
    { duration: "30s", target: 10 }, // ramp down from 20 to 10 VUs in 30s
    { duration: "30s", target: 0 }   // ramp down from 10 to 0 VUs in 30s
  ],
  iterations: 200,       // total number of iterations
  vusMax: 20,            // maximum number of VUs
  startVUs: 5            // initial number of VUs
};

export default function () {
  let res = http.get("https://test.k6.io");

  check(res, {
    "status is 200": (r) => r.status === 200,
    "response time is < 500ms": (r) => r.timings.duration < 500
  });

  sleep(1);
}
```

---

# Important Note: This Script Will Not Work as Written

The above script is useful for understanding the available options, but it is **not a valid final configuration**.

The main issue is that **`stages` should not be combined with `duration` and `iterations` in this way**, because they represent conflicting execution models.

---

# Why These Options Conflict

## 1. `stages` vs `duration`

When you use `stages`, each stage already has its own duration.

For example:

```javascript
stages: [
  { duration: "30s", target: 10 },
  { duration: "30s", target: 20 },
  { duration: "1m", target: 20 },
  { duration: "30s", target: 10 },
  { duration: "30s", target: 0 }
]
```

The total duration of the test is already defined by the sum of all stage durations:

- 30s
- 30s
- 1m
- 30s
- 30s

Total = **3 minutes**

So if you also define:

```javascript
duration: "1m"
```

it creates a conflict, because the test now has **two different duration definitions**.

---

## 2. `stages` vs `iterations`

The `iterations` option tells K6 to stop after a fixed number of total iterations.

Example:

```javascript
iterations: 200
```

But if you are also using `stages`, K6 is expected to follow the full staged load pattern over time.

If the script reaches 200 iterations **before all stages complete**, the test will stop early.  
That makes the staged configuration meaningless.

So, in practice, `iterations` should not be mixed with `stages` in this kind of setup.

---

# Corrected Version of the Script

To use **stages** properly, remove the conflicting `duration` and `iterations` options.

```javascript
import http from "k6/http";
import { check, sleep } from "k6";

export const options = {
  stages: [
    { duration: "30s", target: 10 }, // ramp up to 10 VUs in 30s
    { duration: "30s", target: 20 }, // ramp up from 10 to 20 VUs in 30s
    { duration: "1m", target: 20 },  // stay at 20 VUs for 1 minute
    { duration: "30s", target: 10 }, // ramp down from 20 to 10 VUs in 30s
    { duration: "30s", target: 0 }   // ramp down from 10 to 0 VUs in 30s
  ],
  startVUs: 5
};

export default function () {
  let res = http.get("https://test.k6.io");

  check(res, {
    "status is 200": (r) => r.status === 200,
    "response time is < 500ms": (r) => r.timings.duration < 500
  });

  sleep(1);
}
```

# Code Breakdown

## 1. Importing Modules

```javascript
import http from "k6/http";
import { check, sleep } from "k6";
```

These imports are used for:

- `http` → sending HTTP requests    
- `check` → validating the response

---

## 2. `stages`

```javascript
stages: [
  { duration: "30s", target: 10 },
  { duration: "30s", target: 20 },
  { duration: "1m", target: 20 },
  { duration: "30s", target: 10 },
  { duration: "30s", target: 0 }
]
```

This creates a staged load pattern with **five phases**.

### Stage 1

```javascript
{ duration: "30s", target: 10 }
```

Ramp up to **10 VUs** in **30 seconds**.

### Stage 2

```javascript
{ duration: "30s", target: 20 }
```

Ramp up from **10 VUs to 20 VUs** in **30 seconds**.

### Stage 3

```javascript
{ duration: "1m", target: 20 }
```

Maintain **20 VUs** for **1 minute**.

### Stage 4

```javascript
{ duration: "30s", target: 10 }
```

Ramp down from **20 VUs to 10 VUs** in **30 seconds**.

### Stage 5

```javascript
{ duration: "30s", target: 0 }
```

Ramp down from **10 VUs to 0 VUs** in **30 seconds**.

---

## 3. `startVUs`

```javascript
startVUs: 5
```

This sets the **initial number of Virtual Users** at the beginning of the test.

So instead of starting from 0 users, the test begins with **5 VUs**.

---

## 4. HTTP Request and Validation

```javascript
let res = http.get("https://test.k6.io");

check(res, {
  "status is 200": (r) => r.status === 200,
  "response time is < 500ms": (r) => r.timings.duration < 500
});
```

This part of the script:

- sends a `GET` request to `https://test.k6.io`    
- checks whether the response status is `200`
- checks whether the response time is less than **500 ms**

---

## 5. Simulating User Think Time

```javascript
sleep(1);
```

This pauses the Virtual User for **1 second** before starting the next iteration.

# Understanding the Load Pattern

With the corrected staged configuration, the test behaves like this:

| Stage | Duration | Target VUs | Description                   |
| ----- | -------: | ---------: | ----------------------------- |
| 1     |      30s |         10 | Ramp up to 10 users           |
| 2     |      30s |         20 | Ramp up from 10 to 20 users   |
| 3     |       1m |         20 | Maintain 20 users             |
| 4     |      30s |         10 | Ramp down from 20 to 10 users |
| 5     |      30s |          0 | Ramp down from 10 to 0 users  |

Total test duration = **3 minutes**

- `iterations`

## Key takeaway

Not all options should be combined together in the same script.

### In particular:

- `stages` already controls the duration of the test
- `iterations` can conflict with staged execution
- `duration` can conflict with staged execution

---

# Recommended Practical Rule

Use one of these approaches depending on your test goal:

## Option 1: Fixed load for fixed time

Use:

- `vus`    
- `duration`

## Option 2: Fixed number of executions

Use:

- `vus`
- `iterations`

## Option 3: Variable load over time

Use:

- `stages`
- optionally `startVUs`
