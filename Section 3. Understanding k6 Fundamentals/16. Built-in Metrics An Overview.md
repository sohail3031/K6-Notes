# 1. Metrics in k6

## What Are Metrics?

Metrics in **k6** are specific data points collected during test execution that provide insight into different aspects of application performance.

They help us understand:

- how the application behaves under load
- whether the system is meeting performance expectations
- where performance bottlenecks may exist
- how performance changes across different test scenarios

## Purpose of Metrics

The main purpose of metrics is to **monitor and evaluate the performance and reliability of an application while tests are running**.

By analyzing metrics, we can:

- identify bottlenecks
- track performance improvements
- compare results across multiple test runs
- ensure the application meets performance requirements

## What Metrics Measure

Metrics capture quantitative information such as:

- **response time**
- **throughput**
- **error rate**
- **virtual user concurrency**
- **request count**
- **iteration count**
- **data sent and received**

These measurements allow us to evaluate application performance in a structured way.

---

# 2. Important Built-in Metrics in k6

k6 automatically collects a number of built-in metrics during test execution.

Some of the most commonly used built-in metrics are:

- **`http_reqs`**  
    Total number of HTTP requests made.
- **`http_req_duration`**  
    Total time taken to complete an HTTP request.
- **`http_req_waiting`**  
    Time spent waiting for the server to send the first byte of the response.
- **`http_req_connecting`**  
    Time spent establishing the TCP connection.
- **`iterations`**  
    Number of times the default function was executed.
- **`vus`**  
    Number of currently active virtual users.
- **`vus_max`**  
    Maximum number of virtual users allowed during the test.
- **`data_sent`**  
    Total amount of data sent to the server.
- **`data_received`**  
    Total amount of data received from the server.

These built-in metrics are automatically shown in the console output after running a k6 script.

# 3. Example Script for Built-in Metrics

The following script sends an HTTP GET request and then pauses for 1 second to simulate user think time.

## Code

```javascript
import http from "k6/http";
import { sleep } from "k6";

export default function () {
  http.get("https://test-api.k6.io/public/crocodiles/1/");
  sleep(1);
}
```

---

# 4. Code Explanation

## `import http from "k6/http";`

Imports the **HTTP module** used to send HTTP requests.

## `import { sleep } from "k6";`

Imports the **sleep()** function, which pauses execution for a specified number of seconds.

## `export default function () { ... }`

This is the main function executed by each virtual user.

## `http.get("https://test-api.k6.io/public/crocodiles/1/");`

Sends a **GET request** to the given API endpoint.

## `sleep(1);`

Pauses execution for **1 second** to simulate real user think time between actions.

---

# 5. What Happens When This Script Runs?

When this script is executed:

- k6 sends an HTTP request to the API endpoint
- the script waits for 1 second
- k6 automatically collects built-in metrics during execution
- the results are displayed in the console output

Since this script does **not** contain a `check()` function:

- there will be **no check-related metrics**
- only the default built-in metrics will be displayed

Also, because no **`vus`**, **`duration`**, or **`iterations`** options are explicitly set:

- k6 runs the script with **1 virtual user**
- it performs **1 iteration**

# 8. Important Metrics in the Output

## `http_req_duration`

Represents the total time taken to complete the HTTP request.

It includes:

- connection time
- sending the request
- waiting for the response
- receiving the response

Example:

```text
http_req_duration: avg=130.5ms
```

This means the average request took **130.5 milliseconds**.

---

## `http_req_failed`

Shows the percentage and count of failed HTTP requests.

Example:

```text
http_req_failed: 0.00%  0 out of 2
```

This means **no HTTP requests failed**.

---

## `http_reqs`

Represents the total number of HTTP requests made during the test.

Example:

```text
http_reqs: 2
```

This means **2 HTTP requests** were made.

---

## `iteration_duration`

Shows how long one complete iteration of the script took.

Example:

```text
iteration_duration: avg=2.52s
```

This includes:

- the request execution time
- the `sleep(1)` time
- any other work done inside the iteration

---

## `iterations`

Shows the total number of iterations completed.

Example:

```text

```

This means the script executed **once**.

---

## `vus`

Shows the number of active virtual users during the test.

Example:

```text

```

This means the test ran with **1 virtual user**.

---

## `vus_max`

Shows the maximum number of virtual users configured for the test.

Example:

```text
vus_max: 1
```

This means the maximum number of virtual users was **1**.

---

## `data_received`

Shows the total amount of data received from the server.

Example:

```text

```

# 10. Why Built-in Metrics Matter

Built-in metrics are extremely useful because they allow us to analyze test behavior **without writing extra logic**.

They help answer questions such as:

- How many requests were made?
- How long did each request take?
- Did any requests fail?
- How many virtual users were active?
- How much data was transferred?
- How long did each iteration take?

These metrics form the foundation of performance analysis in k6.

# 11. Introduction to Custom Metrics

In addition to built-in metrics, **k6** also supports **custom metrics**. These are useful when we want to track application-specific behavior that built-in metrics do not cover.

The main types of custom metrics in k6 are:

- **Counter**  
    Used to count the number of times an event occurs.
- **Gauge**  
    Used to measure a value at a specific point in time.
- **Trend**  
    Used to track statistical trends over time, such as durations or sizes.
- **Rate**  
    Used to measure how often something happens, usually in terms of success or failure ratio.

We will cover these custom metrics in the next lecture with separate examples and demos.
