### Overview

This example combines **all 4 K6 custom metrics** in a single script:

- **Counter** → counts successful requests    
- **Gauge** → stores the response time value
- **Trend** → records response time statistics over time
- **Rate** → measures the success ratio of requests

It also introduces **thresholds**, which let K6 decide whether the test should be considered **pass** or **fail** based on performance conditions.

---

# 1) What this script is trying to do

The script:

1. Sends requests to an API endpoint    
2. Tracks **successful requests**
3. Measures **response time**
4. Records **response time trends**
5. Calculates **success rate**
6. Uses **thresholds** to decide whether the test result passes or fails

---

# 2) Corrected K6 Script

```javascript
import http from "k6/http";
import { Counter, Gauge, Trend, Rate } from "k6/metrics";
import { sleep } from "k6";

// custom metrics
const successfulRequests = new Counter("successful_requests");
const responseTimeGauge = new Gauge("response_time_gauge");
const responseTimeTrend = new Trend("response_time_trend");
const successRate = new Rate("success_rate");

// test configuration
export const options = {
  stages: [
    { duration: "10s", target: 5 }, // ramp up to 5 VUs
    { duration: "20s", target: 5 }, // stay at 5 VUs
    { duration: "10s", target: 0 }, // ramp down to 0 VUs
  ],
  thresholds: {
    successful_requests: ["count > 100"],
    response_time_gauge: ["value < 500"],
    response_time_trend: ["p(95) < 500"],
    success_rate: ["rate > 0.9"],
  },
};

export default function () {
  const res = http.get("https://test-api.k6.io/public/crocodiles/1/");
  const isSuccessful = res.status === 200;

  // update custom metrics
  successfulRequests.add(isSuccessful ? 1 : 0);
  responseTimeGauge.add(res.timings.duration);
  responseTimeTrend.add(res.timings.duration);
  successRate.add(isSuccessful);

  sleep(1);
}
```

# 3) What each custom metric does here

## A) Counter → `successful_requests`

```javascript
successfulRequests.add(isSuccessful ? 1 : 0);
```

### Purpose

Counts how many requests were successful.

### How it works

- If response status is **200**, it adds **1**    
- Otherwise, it adds **0**

So after the test, `successful_requests` tells you **how many successful requests happened in total**.

---

## B) Gauge → `response_time_gauge`

```javascript
responseTimeGauge.add(res.timings.duration);
```

### Purpose

Stores the response time value.

### How it works

- `res.timings.duration` gives the total request duration in milliseconds
- That value is added to the gauge metric

### Important note about Gauge

A **Gauge** represents a value at a point in time, but K6 will still show summary stats like min/max/latest in the output.

---

## C) Trend → `response_time_trend`

```javascript
responseTimeTrend.add(res.timings.duration);
```

### Purpose

Tracks response times across all iterations and provides statistics such as:

- average
- minimum
- maximum
- median
- percentiles like **p(95)**

This is useful when you want to analyze how response times behave over the full test run.

---

## D) Rate → `success_rate`

```javascript
successRate.add(isSuccessful);
```

### Purpose

Measures the ratio of successful requests.

### How it works

- `isSuccessful` is `true` when status is 200
- `Rate` tracks how often the value is `true`

If 90 out of 100 requests succeed, the rate becomes **0.90**.

# 5) Understanding thresholds

Thresholds define **performance pass/fail rules** for metrics.

```javascript
thresholds: {
  successful_requests: ["count > 100"],
  response_time_gauge: ["value < 500"],
  response_time_trend: ["p(95) < 500"],
  success_rate: ["rate > 0.9"],
}
```

Let’s break these down.

---

## Threshold 1: `successful_requests`

```javascript
successful_requests: ["count > 100"]
```

### Meaning

The total number of successful requests must be **greater than 100**.

### If true

- threshold passes

### If false

- threshold fails

---

## Threshold 2: `response_time_gauge`

```javascript
response_time_gauge: ["value < 500"]
```

### Meaning

The gauge value should be **less than 500 ms**.

### Important note

Using a threshold like this on a Gauge means the recorded value being evaluated should remain under 500 ms.

---

## Threshold 3: `response_time_trend`

```javascript
response_time_trend: ["p(95) < 500"]
```

### Meaning

**95% of requests** should complete in **less than 500 ms**.

This is one of the most useful performance thresholds because it avoids relying only on average response time.

---

## Threshold 4: `success_rate`

```javascript
success_rate: ["rate > 0.9"]
```

### Meaning

The request success rate must be **greater than 90%**.

So if too many requests fail, this threshold fails.

# 6) Thresholds vs Checks

Your note says:

> Thresholds are same as check method but they used to check conditions after execution is completed.

That idea is **partly right**, but it needs to be made more accurate.

## Correct distinction

### `check()`

- validates conditions **during script execution**
- mainly used for **functional validation**
- does **not fail the test by itself** unless you use it with thresholds or external logic

### `thresholds`

- define **pass/fail criteria for metrics**
- evaluated over the **aggregated test results**
- can make the **whole test fail**

## In short

- **Checks** = validate individual responses/conditions during runtime
- **Thresholds** = define performance rules for the final test outcome
