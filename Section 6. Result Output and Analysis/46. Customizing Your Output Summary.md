The `handleSummary()` function in k6 is not limited to simply exporting the default results. You can also **modify the summary data before printing it**, which allows you to:

- remove metrics you do not want to display    
- hide sub-metrics
- change the formatting of the console output
- customize indentation and colors
- generate a cleaner summary focused only on the metrics you care about

In this lecture, the summary is customized in two ways:

1. **Delete selected metrics from the summary**
2. **Use `textSummary()` to control how the output is displayed in the console**

---

# Code

```javascript
import http from "k6/http";
import { textSummary } from "https://jslib.k6.io/k6-summary/0.0.2/index.js";

export default function() {
	http.get("https://test.k6.io");
}

export function handleSummary(data) {
	delete data.metrics["http_req_duration{expected_response:true}"];
	
	for (const key in data.metrics) {
		if (key.startsWith("iteration")) {
			delete data.metrics[key];
		}
	}
	
	return {
		stdout: textSummary(data, { indent: "->", enableColors: true })
	};
}
```

---

# What this script does

This script performs a GET request to `https://test.k6.io`, and after the test completes, `handleSummary()` customizes the final summary before printing it to the terminal.

The customization includes:

- removing the metric `http_req_duration{expected_response:true}`
- removing all metrics whose names start with `"iteration"`
- printing the remaining summary using `textSummary()`
- applying a custom indent marker (`->`)
- enabling colored output in the console

---

# Step-by-step explanation

## 1. Import `textSummary()`

```javascript
import { textSummary } from "https://jslib.k6.io/k6-summary/0.0.2/index.js";
```

The `textSummary()` function is a helper utility that generates a formatted text version of the k6 summary. It is commonly used inside `handleSummary()` when you want a **clean, readable console summary** with formatting options.

---

## 2. Run the HTTP request

```javascript
export default function() {
	http.get("https://test.k6.io");
}
```

This is the test logic. Each iteration sends an HTTP GET request to the given URL.

---

## 3. Remove a specific sub-metric

```javascript
delete data.metrics["http_req_duration{expected_response:true}"];
```

The `data` object passed to `handleSummary()` contains all aggregated metrics collected during the test.

This line removes the metric:

```javascript
http_req_duration{expected_response:true}
```

### What is this metric?

It is a **sub-metric** of `http_req_duration` filtered for requests where `expected_response:true`.

In other words, it represents request duration values for successful/expected responses only.

### Why delete it?

You might remove it if:

- it is redundant for your report    
- you want a smaller output
- you only care about the overall `http_req_duration`
- you want to simplify the final summary

---

## 4. Remove all metrics starting with `"iteration"`

```javascript
for (const key in data.metrics) {
	if (key.startsWith("iteration")) {
		delete data.metrics[key];
	}
}
```

This loop iterates through all metric names in `data.metrics`.

If a metric name starts with `"iteration"`, it is removed from the summary.

### This typically removes metrics such as:

- `iteration_duration`
- `iterations`

depending on what appears in the summary.

### Why do this?

This is useful if you want the final report to focus more on **HTTP-level metrics** and less on **iteration-level metrics**.

---

# Important note about modifying `data`

Inside `handleSummary()`, the `data` object can be modified before it is passed to `textSummary()` or written to files.

That means you can:

- remove metrics    
- rename data if needed
- extract only selected values
- build your own custom report structure

This makes `handleSummary()` very flexible for reporting.

---

# 5. Print the customized summary

```javascript
return {
	stdout: textSummary(data, { indent: "->", enableColors: true })
};
```

This sends the formatted summary to the terminal.

---

# Understanding `textSummary()` options

## `indent: "->"`

This changes the indentation prefix used in the output.

Normally the summary uses spaces for indentation. Here, each indented line will begin with `->`, making the formatting visually different.

### Example idea:

Instead of something like:

```text
http_req_duration...
  avg=...
```

you may see a structure where indented lines begin with `->`.

---

## `enableColors: true`

This enables colored console output, which makes the summary easier to read in terminals that support ANSI colors.

If you change it to:

```javascript
enableColors: false
```

the output will still work, but it will be plain text without color highlighting.

---

# What the final result looks like conceptually

After the test run:

- k6 gathers all metrics    
- `handleSummary()` receives them
- selected metrics are removed
- the remaining metrics are passed to `textSummary()`
- the terminal shows a **filtered, formatted summary**

So instead of the default full k6 summary, you get a **custom summary with only the metrics you want**.

---

# Important correction to the lecture wording

The lecture refers to deleting from `data.matrix` or “submatrix”, but the correct object is:

```javascript
data.metrics
```

So the customization is done on the **metrics object**, not on a `matrix` object.

---

# What kinds of metrics can be removed?

You can remove any metric that exists in `data.metrics`, for example:

- `http_req_duration`    
- `http_req_blocked`
- `http_req_connecting`
- `http_req_waiting`
- `iterations`
- `iteration_duration`
- `data_sent`
- `data_received`

You can also remove specific tagged sub-metrics such as:

```javascript
data.metrics["http_req_duration{expected_response:true}"]
```

---

# Practical use cases of this customization

## 1. Cleaner console output

If your test produces many metrics, the summary can become noisy. Removing less relevant metrics makes the report easier to scan.

## 2. Focus only on HTTP metrics

You may want the report to emphasize:

- request duration    
- throughput
- failures
- checks

and hide iteration-level metrics.

## 3. CI/CD-friendly output

A smaller summary is easier to read in build logs.

## 4. Team-specific reporting

Different teams care about different metrics:

- QA may care about failures and thresholds
- backend teams may care about latency and throughput
- infra teams may care about concurrency and scaling

You can tailor the summary accordingly.

```javascript
import http from "k6/http";
import { textSummary } from "https://jslib.k6.io/k6-summary/0.0.2/index.js";

export default function() {
	http.get("https://test.k6.io");

export function handleSummary(data) {
	// Remove a tagged sub-metric from the summary
	delete data.metrics["http_req_duration{expected_response:true}"];

	for (const key in data.metrics) {
		if (key.startsWith("iteration")) {
			delete data.metrics[key];

		stdout: textSummary(data, {
```

# Key takeaways

## `handleSummary()` can modify the summary before it is displayed

You are not limited to the default k6 report.

## `data.metrics` contains the aggregated metrics

You can inspect, delete, or extract values from it.

## You can remove unwanted metrics

This helps create a more focused and readable report.

## `textSummary()` gives control over formatting

You can customize:

- indentation
- colors
- final console appearance
