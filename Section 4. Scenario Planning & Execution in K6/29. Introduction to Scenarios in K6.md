### What are Scenarios in K6?

In **k6**, **scenarios** are used to model different user behaviors and load patterns within a single test script. Instead of running one fixed execution pattern for the whole script, scenarios let you define **how Virtual Users (VUs) should execute**, **when they should start**, **how long they should run**, and **what executor should control them**.

This is useful for simulating realistic traffic patterns such as:

- constant user load
- ramping users up and down
- fixed number of shared iterations
- arrival-rate based traffic
- multiple user journeys running in parallel

---

## Why Scenarios are Important

Scenarios help you create more realistic and flexible performance tests by allowing you to:

- **Simulate different user behaviors** in one script    
- **Control load patterns** more precisely
- **Run multiple workflows** in parallel or sequentially
- **Assign different configurations** to different parts of the test
- **Use different executors** depending on the test goal

For example, you might want:

- one scenario for **homepage browsing**
- another scenario for **login flow**
- another scenario for **checkout flow**

Each of these can have its own VUs, duration, executor, tags, and environment variables.

---

# Key Concepts of Scenarios

## 1. Scenario Block

Scenarios are defined inside the `options` object using the `scenarios` property.

```javascript
export const options = {
	scenarios: {
		simple_scenario: {
			// scenario configuration
		}
	}
};
```

- `simple_scenario` is the **scenario name**    
- Each scenario contains its own execution configuration

You can define **one or more scenarios** inside this block.

---

## 2. Executor

The **executor** is the most important part of a scenario.

It controls **how VUs and iterations are scheduled**.

Some common executors are:

- `constant-vus`    
- `ramping-vus`
- `shared-iterations`
- `per-vu-iterations`
- `constant-arrival-rate`
- `ramping-arrival-rate`

In this lecture, the example uses:

```javascript
executor: "constant-vus"
```

This means:

- a fixed number of VUs will run continuously
- they will keep executing the `default` function for the specified duration

---

## 3. VUs

`vus` defines how many virtual users should run concurrently.

```javascript
vus: 10
```

This means:

- **10 virtual users** will run at the same time    

---

## 4. Duration

`duration` defines how long the scenario should run.

```javascript
duration: "30s"
```

This means:

- the scenario will run for **30 seconds**    

---

## 5. startTime

`startTime` is used to delay when a scenario begins.

Example:

```javascript
startTime: "10s"
```

This means:

- the scenario will start **10 seconds after the test begins**    

This is useful when you want scenarios to run **sequentially** instead of all starting at once.

---

## 6. gracefulStop

`gracefulStop` defines how long k6 should wait for iterations to finish before forcefully stopping them.

Example:

```javascript
gracefulStop: "5s"
```

This means:

- when the scenario duration ends, k6 will allow **up to 5 more seconds** for in-progress iterations to finish gracefully    

---

## 7. env

You can define **environment variables specific to a scenario** using `env`.

Example:

```javascript
env: {
	EXAMPLE_VAR: "testing"
}
```

These variables can then be accessed in the script using `__ENV.EXAMPLE_VAR`.

This is useful when different scenarios need different configuration values.

---

## 8. tags

You can attach **tags** to a scenario for filtering and reporting.

Example:

```javascript
tags: {
	example_tag: "testing"
}
```

These tags help categorize results in reports and metrics.

---

# Example 1: Basic Scenario Using `constant-vus`

```javascript
import http from "k6/http";
import { sleep } from "k6";

export const options = {
	scenarios: {
		simple_scenario: {
			executor: "constant-vus",
			vus: 10, // number of VUs to run concurrently
			duration: "30s" // duration for script to run
		}
	}
};

export default function() {
	http.get("https://test.k6.io");
	
	sleep(1);
}
```

---

# Explanation of the Script

## Import Statements

```javascript
import http from "k6/http";
import { sleep } from "k6";
```

- `http` is used to make HTTP requests    
- `sleep()` pauses the VU for a specified time

---

## Defining the Scenario

```javascript
export const options = {
	scenarios: {
		simple_scenario: {
			executor: "constant-vus",
			vus: 10,
			duration: "30s"
		}
	}
};
```

### Breakdown:

### `scenarios`

This tells k6 that we are defining custom execution scenarios.

### `simple_scenario`

This is the **name of the scenario**.  
You can give it any meaningful name.

### `executor: "constant-vus"`

This executor keeps a **constant number of VUs** running throughout the scenario duration.

### `vus: 10`

This tells k6 to run **10 concurrent virtual users**.

### `duration: "30s"`

This tells k6 to keep those VUs active for **30 seconds**.

---

## Default Function

```javascript
export default function() {
	http.get("https://test.k6.io");
	sleep(1);
}
```

This is the code executed by every VU repeatedly during the scenario.

### What happens here?

1. Each VU sends a GET request to `https://test.k6.io`    
2. The VU then waits for **1 second**
3. After that, the VU repeats the same process until the scenario duration ends

Since we have **10 VUs** running for **30 seconds**, all of them will keep looping through this function during that time.

---

# How This Scenario Executes

With the configuration:

```javascript
executor: "constant-vus",
vus: 10,
duration: "30s"
```

k6 will:

- start **10 virtual users**    
- keep all 10 VUs active for **30 seconds**
- each VU will repeatedly execute the `default()` function
- in each loop:
    - it sends an HTTP request
    - sleeps for 1 second
    - repeats again

# Common Scenario Configuration Options

Below are some commonly used scenario properties:

| Option         | Purpose                                           |
| -------------- | ------------------------------------------------- |
| `executor`     | Defines how VUs/iterations are scheduled          |
| `vus`          | Number of virtual users                           |
| `duration`     | How long the scenario should run                  |
| `iterations`   | Total number of iterations to execute             |
| `maxDuration`  | Maximum time allowed for a scenario               |
| `startTime`    | Delay before starting the scenario                |
| `gracefulStop` | Time allowed for in-progress iterations to finish |
| `env`          | Scenario-specific environment variables           |
| `tags`         | Scenario-specific tags for reporting/filtering    |

---

# Example of a More Detailed Scenario Configuration

Below is a more complete example showing additional scenario properties:

```javascript
export const options = {
	scenarios: {
		example_scenario: {
			executor: "shared-iterations",
			vus: 10,
			iterations: 200,
			maxDuration: "10s",
			startTime: "10s",
			gracefulStop: "5s",
			env: {
				EXAMPLE_VAR: "testing"
			},
			tags: {
				example_tag: "testing"
			}
		}
	}
};
```

---

# Explanation of This Advanced Scenario

## `executor: "shared-iterations"`

This executor distributes a **fixed number of iterations** among the specified VUs.

## `vus: 10`

10 virtual users will participate in executing the scenario.

## `iterations: 200`

The scenario must complete **200 total iterations**.

## `maxDuration: "10s"`

The scenario will be forcefully stopped if it does not finish within **10 seconds**.

## `startTime: "10s"`

The scenario starts **10 seconds after the test begins**.

## `gracefulStop: "5s"`

Allows ongoing iterations to finish within **5 extra seconds** before stopping.

## `env`

Defines environment variables specific to this scenario.

## `tags`

Adds metadata tags for filtering and reporting.

# Parallel vs Sequential Scenarios

## Parallel Execution

By default, if multiple scenarios are defined without `startTime`, they run **in parallel**.

Example:

```javascript
export const options = {
	scenarios: {
		scenario_one: {
			executor: "constant-vus",
			vus: 5,
			duration: "20s"
		},
		scenario_two: {
			executor: "constant-vus",
			vus: 3,
			duration: "20s"
		}
	}
};
```

Both scenarios start together.

---

## Sequential Execution

You can make scenarios run one after another using `startTime`.

Example:

```javascript
export const options = {
	scenarios: {
		login_flow: {
			executor: "constant-vus",
			vus: 5,
			duration: "10s"
		},
		checkout_flow: {
			executor: "constant-vus",
			vus: 5,
			duration: "10s",
			startTime: "10s"
		}
	}
};
```

Here:

- `login_flow` starts immediately    
- `checkout_flow` starts after **10 seconds**

---

# When to Use Scenarios

Scenarios are useful when you want to:

- simulate **multiple user journeys**    
- apply **different load models** in the same test
- run **API and UI-like flows separately**
- combine **steady load + spike load**
- schedule tests **sequentially or in parallel**
- isolate different business workflows with different VU strategies

---

# Quick Summary

In this lecture, we learned that:

- **Scenarios** are used in k6 to define **custom load patterns and workflows**    
- Scenarios are defined inside the `options.scenarios` object
- Each scenario can have its own:
    - **executor**
    - **VUs**
    - **duration**
    - **iterations**
    - **start time**
    - **tags**
    - **environment variables**
- The **executor** determines how the scenario behaves
- The `constant-vus` executor keeps a fixed number of VUs active for a specified duration
- Multiple scenarios can be run in **parallel** or **sequentially**
