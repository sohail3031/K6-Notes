## **What this topic is about**

In k6, a single test can simulate **different real-world traffic behaviors at the same time** using **scenarios**.  
Each scenario can behave differently based on:

- number of virtual users (VUs)
- request rate
- time pattern (steady, ramping, burst)

This helps you simulate **real production traffic instead of uniform load**.

---

# **1. Constant Load Scenario**

```javascript
constant_load: {
	executor: "constant-vus",
	vus: 5,
	duration: "20s"
}
```

## What it does:

- Keeps **5 virtual users running continuously**
- Each VU keeps executing requests for **20 seconds**
- Load remains **stable (flat line graph)**

## Why it is used:

- Baseline performance testing
- Checking system stability under steady traffic

## Real-world mapping:

👉 5 users continuously browsing a website

---

# **2. Ramping Load Scenario**

```javascript
ramping_load: {
	executor: "ramping-vus",
	startVUs: 1,
	stages: [
		{ duration: "10s", target: 10 },
		{ duration: "10s", target: 0 }
	]
}
```

## What it does:

- Starts with **1 VU**
- Gradually increases to **10 VUs in 10s**
- Then decreases back to **0 VUs in next 10s**

## Why it is used:

- To test **system behavior under gradual stress**
- Detect performance degradation over time

## Real-world mapping:

👉 Traffic slowly increases during sale time, then drops after peak

---

# **3. Arrival Rate Scenario (Constant Request Load)**

```javascript
arrival_rate: {
	executor: "constant-arrival-rate",
	rate: 10,
	timeUnit: "1s",
	duration: "20s",
	preAllocatedVUs: 5,
	maxVUs: 20
}
```

## What it does:

- Sends **10 iterations per second**
- Maintains constant request rate regardless of VUs
- Dynamically increases VUs if needed (up to 20 max)

## Why it is used:

- To simulate **API traffic load (TPS-based testing)**
- Ensures system handles fixed throughput

## Real-world mapping:

👉 10 API requests per second continuously hitting backend

---

# **How k6 executes these scenarios together**

When you run:

```bash
k6 run script.js
```

### All scenarios:

- Run **in parallel**
- Start independently
- End based on their own duration rules

So:

- Constant load → steady traffic
- Ramping load → changing traffic curve
- Arrival rate → fixed request throughput

# **Key Learning Insight**

## k6 scenarios separate:

| Concept    | Meaning                    |
| ---------- | -------------------------- |
| VUs        | Simulated users            |
| Iterations | Number of executions       |
| Rate       | Requests per second        |
| Stages     | Load progression over time |

# **Why this approach is powerful**

Instead of running one boring test, you can simulate:

- Normal users (constant load)
- Peak traffic (ramping load)
- API stress (arrival rate)

This gives a **real production-like performance picture**, not just synthetic load.

# **Final Summary**

This script demonstrates 3 load strategies:

- **constant-vus → steady users**
- **ramping-vus → changing load over time**
- **constant-arrival-rate → fixed request throughput**

Together, they help test:

- scalability
- stability
- throughput handling
- real-world traffic behavior
