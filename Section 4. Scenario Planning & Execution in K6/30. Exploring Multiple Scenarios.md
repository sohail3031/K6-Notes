### Introduction

In **k6**, you can define **multiple scenarios** within a single test script. This is extremely useful when you want to simulate **different user behaviors or traffic patterns** in the same load test.

For example:

- one scenario can simulate **users browsing the website**    
- another scenario can simulate **users performing purchases**
- another scenario can simulate **login requests**
- another scenario can simulate **background API traffic**

This makes your performance test much more realistic because real applications usually have **different kinds of users doing different things at different times**.

---

# Why Use Multiple Scenarios?

Multiple scenarios help you:

- simulate **different workflows** in one test    
- apply **different executors** for different user journeys
- start scenarios at **different times**
- combine **different load models**
- create **more realistic test behavior**
- isolate and compare **different traffic patterns**

---

# Example: Two Scenarios in a Single k6 Script

```javascript
import http from "k6/http";

export const options = {
	scenarios: {
		shared_iter_scenario: {
			executor: "shared-iterations",
			vus: 10,
			iterations: 100,
			startTime: "0s"
		},
		per_vu_scenario: {
			executor: "per-vu-iterations",
			vus: 10,
			iterations: 10,
			startTime: "10s"
		}
	}
};

export default function() {
	http.get("https://test.k6.io");
}
```

---

# What This Script Does

This script defines **two scenarios**:

1. **`shared_iter_scenario`**    
2. **`per_vu_scenario`**

Both scenarios call the same `default()` function, which sends a GET request to:

```javascript
https://test.k6.io
```

However, **the way they execute is different**, because they use **different executors** and **different start times**.

---

# Step-by-Step Explanation

---

# 1. Import HTTP Module

```javascript
import http from "k6/http";
```

This imports the **HTTP module**, which is used to make HTTP requests.

---

# 2. Defining Multiple Scenarios

```javascript
export const options = {
	scenarios: {
		shared_iter_scenario: {
			executor: "shared-iterations",
			vus: 10,
			iterations: 100,
			startTime: "0s"
		},
		per_vu_scenario: {
			executor: "per-vu-iterations",
			vus: 10,
			iterations: 10,
			startTime: "10s"
		}
	}
};
```

Inside `options.scenarios`, we define two separate scenarios.

---

# Scenario 1: `shared_iter_scenario`

```javascript
shared_iter_scenario: {
	executor: "shared-iterations",
	vus: 10,
	iterations: 100,
	startTime: "0s"
}
```

## Explanation

This scenario uses the **`shared-iterations`** executor.

### Meaning of `shared-iterations`

This executor runs a **fixed total number of iterations**, and those iterations are **shared among all VUs**.

### In this case:

- `vus: 10` → 10 virtual users will participate    
- `iterations: 100` → total 100 iterations will be executed
- `startTime: "0s"` → this scenario starts immediately when the test begins

### Important point:

The **100 iterations are shared across the 10 VUs**.

That means:

- one VU might run 12 iterations
- another might run 8
- another might run 15

There is **no guarantee** that each VU will execute the same number of iterations.

The only guarantee is that the **total scenario iterations = 100**.

---

# Scenario 2: `per_vu_scenario`

```javascript
per_vu_scenario: {
	executor: "per-vu-iterations",
	vus: 10,
	iterations: 10,
	startTime: "10s"
}
```

## Explanation

This scenario uses the **`per-vu-iterations`** executor.

### Meaning of `per-vu-iterations`

This executor runs a **fixed number of iterations for each VU**.

### In this case:

- `vus: 10` → 10 virtual users will participate    
- `iterations: 10` → each VU runs 10 iterations
- `startTime: "10s"` → this scenario starts **10 seconds after the test begins**

### Total iterations here:

Since each VU runs 10 iterations and there are 10 VUs:

	10 VUs×10 iterations each=100 total iterations

So this scenario also performs **100 total iterations**, but the execution model is different.

---

# Difference Between the Two Scenarios

## Scenario 1 → `shared-iterations`

- total iterations = **100**    
- shared among **10 VUs**
- each VU may execute **different number of iterations**
- starts at **0s**

## Scenario 2 → `per-vu-iterations`

- each VU executes **10 iterations**    
- total = **10 × 10 = 100**
- every VU executes the **same number of iterations**
- starts at **10s**

---

# Default Function

```javascript
export default function() {
	http.get("https://test.k6.io");
}
```

This is the code executed by both scenarios.

Whenever a VU runs an iteration, it performs:

- an HTTP GET request to `https://test.k6.io`    

Since both scenarios use the same `default()` function, both of them execute the same request logic, but under different scenario configurations.

---

# Execution Timeline of This Script

## At time `0s`

- `shared_iter_scenario` starts immediately    
- 10 VUs begin working on **100 shared iterations**

## Between `0s` and `10s`

- only the first scenario is active

## At time `10s`

- `per_vu_scenario` starts
- 10 VUs begin executing **10 iterations each**

So effectively:

- scenario 1 starts first
- scenario 2 starts later
- both belong to the same test script

# Shared Iterations vs Per-VU Iterations

| Feature                  | `shared-iterations`                                | `per-vu-iterations`                            |
| ------------------------ | -------------------------------------------------- | ---------------------------------------------- |
| Iteration distribution   | Shared among all VUs                               | Fixed per VU                                   |
| Total iterations         | Explicitly specified for whole scenario            | Calculated as `vus × iterations`               |
| Equal iterations per VU? | No                                                 | Yes                                            |
| Use case                 | When total work matters more than per-user balance | When each VU should do the same amount of work |

---

# When to Use `shared-iterations`

Use **`shared-iterations`** when:

- you want a **fixed total number of iterations**    
- you don’t care how they are distributed across VUs
- you want the workload to be completed as fast as possible by the available VUs

Example:

- “Run 500 login requests using 20 users”    

---

# When to Use `per-vu-iterations`

Use **`per-vu-iterations`** when:

- you want **every VU to perform the same amount of work**    
- you want predictable per-user execution
- you are simulating user-specific flows where each user must complete a defined number of steps

Example:

- “Each of 50 users should submit 5 forms”

# Real-World Example: E-Commerce Website

Suppose you are testing an e-commerce application.

You may want:

- one scenario for **users browsing products**    
- one scenario for **users adding items to cart**
- one scenario for **users placing orders**

Example behavior:

- browsing starts immediately
- cart actions begin after some browsing activity
- purchase activity begins later

This is exactly where **multiple scenarios** become very powerful.

For example:

- **Scenario 1:** Browsing traffic starts at `0s`
- **Scenario 2:** Add-to-cart traffic starts at `15s`
- **Scenario 3:** Checkout traffic starts at `30s`

This better reflects how real users behave.

# Important Takeaways from This Lecture

## 1. Multiple scenarios can be defined in one k6 script

This allows you to model different user behaviors in a single test.

## 2. Each scenario can use a different executor

For example:

- one scenario can use `shared-iterations`    
- another can use `per-vu-iterations`
- another can use `constant-vus`

## 3. Each scenario can start at a different time

Using `startTime`, you can delay the execution of specific scenarios.

## 4. Different scenarios can represent different user journeys

For example:

- browsing
- login
- checkout
- API calls
- admin actions
