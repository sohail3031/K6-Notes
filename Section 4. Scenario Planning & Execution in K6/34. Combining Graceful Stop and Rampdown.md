## **What this topic means**

In real performance tests, you often have:

- steady load    
- ramping load
- request-rate load

Each behaves differently when stopping.

So k6 provides **two different “safe shutdown” mechanisms**:

| Feature          | Purpose                               |
| ---------------- | ------------------------------------- |
| gracefulStop     | safely ends a scenario after duration |
| gracefulRampDown | safely reduces VUs during ramping     |

When combined, they ensure:  
👉 no abrupt request termination anywhere in the test

---

# **Correct Combined Code**

```javascript
import http from "k6/http";
import { sleep } from "k6";

export const options = {
	scenarios: {
		constant_load: {
			executor: "constant-vus",
			vus: 5,
			duration: "20s",
			gracefulStop: "5s"
		},

		ramping_load: {
			executor: "ramping-vus",
			startVUs: 1,
			stages: [
				{ duration: "10s", target: 10 },
				{ duration: "10s", target: 0 }
			],
			gracefulRampDown: "5s"
		},

		arrival_rate: {
			executor: "constant-arrival-rate",
			rate: 10,
			timeUnit: "1s",
			duration: "20s",
			preAllocatedVUs: 5,
			maxVUs: 20
		}
	}
};

export default function () {
	http.get("https://test.k6.io");
	sleep(1);
}
```

---

# **Why this combination works**

## ✔ constant_load → uses `gracefulStop`

- Ensures active VUs finish work after 20s    
- Prevents sudden termination

---

## ✔ ramping_load → uses `gracefulRampDown`

- Ensures VUs finish work while scaling down    
- Prevents abrupt cut-off during stage transition

---

## ✔ arrival_rate → no graceful setting needed

- It is rate-controlled    
- k6 manages VUs dynamically internally

---

# **Execution behavior (simple flow)**

### 1. constant_load

- Runs 5 VUs for 20s
- Stops → waits 5s (`gracefulStop`)

### 2. ramping_load

- 1 → 10 VUs
- 10 → 0 VUs
- waits 5s during ramp down (`gracefulRampDown`)

### 3. arrival_rate

- Sends 10 iterations/sec
- runs for 20s
- dynamically scales VUs as needed

---

# **Key Insight (important for exams/interviews)**

✔ gracefulStop → applies at **scenario end**  
✔ gracefulRampDown → applies **between ramp stages**  
✔ they can coexist in same test safely  
✔ they affect **different execution phases**

---

# **Why this matters in real testing**

Without these:

- API requests may get cut mid-flight ❌
- metrics become inaccurate ❌
- transaction failures appear artificially ❌

With both:

- clean shutdown ✔
- realistic traffic simulation ✔
- reliable performance results ✔
